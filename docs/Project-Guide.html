1. Introduction — What Is This Project?

This project is a Multi-Tenant Business Platform. A "multi-tenant" system is one software application that can serve many separate organizations (called tenants) at the same time, while keeping their data private from each other.

Analogy: Think of an apartment building. One building (the software) has many apartments (tenants). Each family lives privately in its own apartment, but they all share the same building infrastructure — elevators, water, electricity.

The platform provides three separate user interfaces (portals):

  • Admin Portal — for system administrators who manage tenants and users.
  • Provider Portal — for service providers (e.g., doctors, staff).
  • Patient Portal — for end users (e.g., patients/customers).

On the back end, the platform uses several small services (microservices) that talk to each other, share a database, and send notifications (emails/SMS) through a message queue.

3. Project Architecture Overview

The project is split into small services. Each service has one job. This is called microservices architecture.

Backend Microservices

  • service-registry — Eureka server (the phone book). Port 8761.
  • api-gateway — Entry point for all API calls. Port 8085.
  • access-security-service — Manages users, tenants, and security. Port 8082.
  • admin-service — Admin operations. Port 8084.
  • business-service — Core business logic; sends events to Kafka. Port 8081.
  • notification-service — Listens to Kafka and sends emails/SMS. Port 8083.
  • platform-core — A shared library (common code used by all services).

Frontends (React)

  • admin-portal — Port 3000
  • provider-portal — Port 3001
  • patient-portal — Port 3002

Infrastructure Containers

  • postgres — Database.
  • keycloak — Login server.
  • redis — Cache.
  • kafka + zookeeper — Messaging system.

4. Docker Explanation

What is Docker? (for total beginners)

Analogy: Imagine packing your entire kitchen — fridge, oven, ingredients, recipes — into one sealed box. You can ship that box anywhere in the world and it will cook the same dish. Docker does this for software. A "container" is that sealed box.

  • Image = the recipe/blueprint.
  • Container = a running copy of the image.
  • Dockerfile = instructions to build an image.
  • docker-compose.yml = instructions to start many containers together.

Backend Dockerfile (example: access-security-service)

FROM maven:3.9-eclipse-temurin-17-alpine AS build      # Stage 1: builder
WORKDIR /workspace
COPY pom.xml ./pom.xml
COPY platform-core ./platform-core
COPY access-security-service ./access-security-service
RUN mvn -f access-security-service/pom.xml package -DskipTests

FROM eclipse-temurin:17-jre-alpine                     # Stage 2: runtime
WORKDIR /app
COPY --from=build /workspace/access-security-service/target/*.jar app.jar
EXPOSE 8082
ENTRYPOINT ["java", "-jar", "app.jar"]

Why two stages? The first stage has the heavy Java compiler. The second stage keeps only the compiled app, making the final image small and fast.

Frontend Dockerfile (example: patient-portal)

FROM node:18-alpine AS build                # Stage 1: build the React app
WORKDIR /app
COPY patient-portal/package.json ./
RUN npm install --legacy-peer-deps
COPY patient-portal/ .
RUN npm run build                           # Produces /app/build (static files)

FROM nginx:alpine                           # Stage 2: serve files
COPY --from=build /app/build /usr/share/nginx/html
COPY patient-portal/nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

React is compiled into plain HTML/JS/CSS files, then Nginx serves them. Very light and fast.

docker-compose.yml — What It Does

This single file starts 14 containers together and connects them on one network called platform-network. Each container can talk to others using its service name (like a domain name).

Key Parts

  • services: list of containers to run.
  • ports: maps host port : container port. Example "8085:8085" means your computer's 8085 connects to the container's 8085.
  • environment: config values (DB password, URLs, etc).
  • depends_on: start order (e.g., Postgres before backend).
  • volumes: storage that survives container restart (like the DB data).
  • networks: all services share platform-network so they can reach each other.

5. How the System Runs (Step-by-Step)

When you run docker compose up --build on a fresh machine, here is what happens:

  1. Build stage: Docker reads each Dockerfile and builds images for every service (Java services get compiled; React apps get built).
  2. Network creation: Docker creates the platform-network.
  3. Volumes: A persistent volume postgres-data is created for the database.
  4. Start order (controlled by depends_on):
    1. postgres, zookeeper, redis start first.
    2. kafka starts after zookeeper.
    3. keycloak starts after postgres and imports the realm file.
    4. service-registry (Eureka) starts.
    5. All backend microservices start and register with Eureka.
    6. api-gateway starts and discovers services from Eureka.
    7. React portals start (served by Nginx).
  5. Ready: You open http://localhost:3000 (or 3001/3002) in your browser and use the app.
Tip: The first build takes 5–15 minutes because Maven and npm download many dependencies. Subsequent builds are much faster thanks to Docker's cache.

6. How Services Communicate

Frontend → Backend

  1. User opens a React portal (e.g., localhost:3000).
  2. React calls http://localhost:8085/api/... using axios.
  3. API Gateway receives the request, checks the JWT token, and forwards it to the correct microservice.

Backend → Database

  • Spring Boot services use JPA/Hibernate to talk to PostgreSQL.
  • Connection URL (inside Docker): jdbc:postgresql://postgres:5432/platform_db.
  • The hostname postgres works because all containers share the same Docker network.

Backend ↔ Backend (via Eureka)

  • Each service registers itself with Eureka at startup.
  • To call another service, a service asks Eureka "where is business-service?" and gets back an address.

Async Messaging (Kafka)

business-service publishes events (e.g., "new tenant created") to a Kafka topic. notification-service listens to that topic and sends an email or SMS. This is called event-driven architecture.

Authentication Flow

  1. User enters username/password in the React portal.
  2. Request goes to Keycloak (localhost:8080).
  3. Keycloak validates and returns a JWT (a signed token).
  4. React stores the JWT (in Zustand auth store) and attaches it to every future API call as Authorization: Bearer <token>.
  5. API Gateway and microservices verify the JWT on each request.

7. How to Run the Project on Another System

Prerequisites

  • Docker Desktop (Windows/Mac) or Docker Engine + Docker Compose v2 (Linux).
  • At least 8 GB RAM free and ~10 GB disk space.
  • Ports 3000, 3001, 3002, 5433, 8080–8085, 8761, 9092 must be free.

Steps

# 1. Copy the entire project folder to the new machine
git clone <repo-url>
cd "Multi-Tenant Business Platform with Notifications"

# 2. (Optional) create a .env file to override defaults
#    POSTGRES_PASSWORD=mypass
#    KEYCLOAK_ADMIN_PASSWORD=mypass

# 3. Build and start everything
docker compose up --build -d

# 4. Check status
docker compose ps

# 5. Open the portals
#    http://localhost:3000  (admin)
#    http://localhost:3001  (provider)
#    http://localhost:3002  (patient)

Mandatory Files

  • Root pom.xml and all service pom.xml files.
  • All Dockerfiles.
  • docker-compose.yml.
  • platform-core/ source code (shared library).
  • keycloak/realms/*.json (realm import).
  • Each portal's package.json, nginx.conf, and src/.

Images: Built or Pulled?

  • Base images (postgres, keycloak, nginx, node, maven, redis, kafka) are pulled from Docker Hub automatically.
  • Your service images are built locally from the Dockerfiles.

Database Data

Data is stored in the named volume postgres-data. To move it between machines:

# Backup
docker run --rm -v postgres-data:/data -v $(pwd):/backup \
  alpine tar czf /backup/db.tgz /data

# Restore on new machine (after compose up)
docker run --rm -v postgres-data:/data -v $(pwd):/backup \
  alpine tar xzf /backup/db.tgz -C /

10. Summary

This project is a full-stack, containerized platform that demonstrates modern microservice architecture. Three React frontends talk to a Spring Boot backend through a single API Gateway, protected by Keycloak authentication. Backend services find each other via Eureka, share a PostgreSQL database, cache with Redis, and communicate asynchronously through Kafka. Everything runs in Docker containers on a shared network, making it easy to start the entire system with a single command.

Quick Revision — High-Level Summary

What is this project?

A cloud-style platform where many organizations (tenants) use one application. Each tenant has its own users and data, but they all share the same infrastructure.

The Three Layers

  1. Frontend — 3 React apps (admin, provider, patient) served by Nginx on ports 3000/3001/3002.
  2. Backend — 6 Spring Boot microservices + Eureka + API Gateway + Keycloak.
  3. Data & Messaging — PostgreSQL (database), Redis (cache), Kafka (events).

docker compose up --build -d    # build + start everything
docker compose ps               # see container status
docker compose logs -f <svc>    # tail logs of one service
docker compose down             # stop and remove containers
docker compose down -v          # also delete DB volume (DANGEROUS)

Remember These 5 Ideas

  1. Docker packages software so it runs identically on any machine.
  2. Microservices = many small apps, each doing one thing, working together.
  3. API Gateway = a single front door to the backend.
  4. Eureka = a phone book so services can find each other.
  5. Kafka = a reliable post office between services (async messages).
One-line takeaway: The project is a Dockerized multi-tenant platform where a React frontend talks to Java microservices via an API Gateway, secured by Keycloak, backed by PostgreSQL, cached by Redis, and connected by Kafka — all started with a single docker compose up command.
